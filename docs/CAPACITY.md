# CAPACITY — сколько выдержит сервер

Ответ на вопрос «сколько людей можно привести, пока всё не легло». Модель
построена на **замеренных** числах из прод-логов, а не на догадках; ниже
показано, откуда взялась каждая цифра, чтобы её можно было пересчитать, когда
условия изменятся.

← [Индекс проекта (PROJECT.md)](PROJECT.md) · смежное: [07-scaling](tasks/07-scaling.md)

---

## 1. Что измерено (прод, 2026-07-29/30)

| Ролик | Куски | Распознавание | Источник |
|---|---|---|---|
| 31 с | 1 | 28.6–29.1 с | `fly logs`, три прогона подряд |
| 551 с | 4 (параллельно 3) | 98 с | `fly logs`, первый длинный ролик |

Из двух точек выводятся два параметра — они и есть основа всей модели:

```
время куска = накладные + длительность / скорость

31 с:   накладные + 31/S  = 29
180 с:  накладные + 180/S = 75      (98 с = волна из 3 кусков + короткий хвост)
→ S ≈ 3.2× реального времени, накладные ≈ 19 с на кусок
```

**19 секунд накладных** — это очередь Runpod и подъём контейнера (FlashBoot
держит воркер тёплым, но не мгновенным). **3.2×** — чистая скорость GPU.

Важное следствие: на коротких роликах накладные съедают почти всё (31 с аудио
за 29 с — это 1.07× реального времени), на длинных — размазываются
(551 с за 98 с — это 5.6×). Поэтому пропускная способность зависит от того,
какие ролики шлют, и ниже считается по «рабочему» случаю в 3 минуты.

Проверить текущие значения в любой момент:

```bash
fly ssh console -C "python -m app.events summary --days 7"
```

Строка `обработка … (xN.NN от длительности)` — это тот самый коэффициент;
если он пополз вверх, узкое место уже наступило.

## 2. Где именно упрётся (по порядку)

### Ограничитель 1 — Max Workers у Runpod (главный)

Шлюз режет длинное аудио и шлёт до `KZSUB_CHUNK_CONCURRENCY = 3` кусков
параллельно. **Один** десятиминутный ролик уже занимает 3 воркера. При
`Max Workers = 2` куски встают в очередь внутри самого запроса.

Пропускная способность одного воркера на кусках по 180 с:

```
180 / (180/3.2 + 19) ≈ 2.4 минуты аудио на минуту работы
```

| Max Workers | Пропускная способность | Стоимость простоя |
|---|---|---|
| 2 (сейчас) | ~4.8 мин аудио / мин | $0 — оплата посекундная |
| 5 | ~12 мин аудио / мин | $0 |
| 10 | ~24 мин аудио / мин | $0 |

**Это денежный рычаг, а не стена.** Runpod платится за секунды работы: поднять
Max Workers ничего не стоит, пока запросов нет. Менять — в консоли эндпоинта,
без деплоя.

### Ограничитель 2 — память шлюза (1 ГБ)

На каждый прогон в памяти лежат: исходный файл, конвертированный WAV и base64
кусков. Оценка пика:

| Что прислала панель | Пик на один прогон |
|---|---|
| 16 kHz mono, 10 мин (свежая панель, ~19 МБ) | ~60–80 МБ |
| 48 kHz stereo, 10 мин (панель до 1.4.0, ~115 МБ) | ~300–400 МБ |

При базовом расходе Python/uvicorn ~200 МБ свободно остаётся ~800 МБ. Отсюда
`KZSUB_MAX_CONCURRENT_JOBS = 2`: два «тяжёлых» (старых) прогона ещё влезают,
три — уже риск OOM. Это уже случалось на 512 МБ (см. CHANGELOG).

### Ограничитель 3 — одна машина Fly

`min_machines_running = 1`, лицензии и метрики лежат в SQLite на томе этой
машины. **Вторую машину поднимать нельзя**, пока хранилище — SQLite: два
процесса на разных машинах не увидят БД друг друга. Переход на Postgres описан
в [07-scaling](tasks/07-scaling.md).

Ограничитель одновременности (`app/limits.py`) тоже живёт в процессе — то есть
считает «на машину». При одной машине это и есть глобальный лимит.

## 3. Сколько это в пользователях

Считаем для Standard: 60 минут аудио в месяц на человека.

При `Max Workers = 2` пропускная способность — 4.8 мин аудио на минуту, то есть
**288 минут аудио в час**.

Монтажёры работают неравномерно: примем, что на пиковый час приходится ~20 %
дневного объёма (вечер). Тогда упор наступает не по месячному объёму, а по
пиковому часу:

```
пиковый час:  288 мин аудио
дневной объём: 288 / 0.20 ≈ 1 440 мин
месячный:      ≈ 43 000 мин
пользователей: 43 000 / 60 ≈ 700
```

| Max Workers | Активных Standard-пользователей | Что происходит на границе |
|---|---|---|
| **2 (сейчас)** | **~700** | в пиковый час ролики ждут в очереди |
| 5 | ~1 700 | то же, порог выше |
| 10 | ~3 500 | упрётся память шлюза → поднимать VM |

**Граница — это очередь, а не падение.** При перегрузе пользователь ждёт
дольше, а после `KZSUB_JOB_WAIT_SECONDS` (120 с) получает «сервис занят,
попробуйте через минуту» — не пятисотку и не молчание.

### А что реально «убивает» сервер

Не поток пользователей, а отдельные запросы. Обе дыры закрыты
(см. [SECURITY.md](SECURITY.md)):

- загрузка гигабайтного тела **без ключа** — заполняла диск раньше, чем
  проверялась лицензия; теперь режется по `Content-Length` до разбора формы;
- несколько тяжёлых прогонов разом — OOM; теперь ограничены очередью.

## 4. Что крутить и в каком порядке

1. **Max Workers у Runpod: 2 → 5.** Ноль кода, ноль простоя, оплата только за
   фактические секунды. Первое, что делать при росте.
2. **`KZSUB_CHUNK_CONCURRENCY`** держать не больше Max Workers — иначе куски
   одного ролика конкурируют между собой же.
3. **VM шлюза 1 ГБ → 2 ГБ** и `KZSUB_MAX_CONCURRENT_JOBS` 2 → 6. Правка
   `fly.toml` + один секрет.
4. **Очередь задач, Postgres, объектное хранилище** — [07-scaling](tasks/07-scaling.md).
   Нужно только когда одной машины перестанет хватать; раньше — лишняя сложность.

## 5. Как перепроверить на своих числах

Модель держится на двух замерах. Когда изменится модель, железо или профиль
роликов — пересними их:

```bash
fly ssh console -C "python -m app.events summary --days 7"
fly logs -a kzsub-gateway | grep "Аудио"
```

Подставь новые «накладные» и «скорость» в формулу из §1 — остальные таблицы
пересчитываются из них.

## Заметки

- Цифра «700 пользователей» опирается на два допущения: 60 минут в месяц на
  человека и 20 % дневного объёма в пиковый час. Оба взяты из здравого смысла,
  а не из данных — реальный профиль появится в `app/events.py` после первых
  десятков клиентов, и тогда цифру надо пересчитать.
- Себестоимость минуты аудио при 3.2× ≈ 19 GPU-секунд. Она НЕ растёт от числа
  пользователей — Runpod платится посекундно, поэтому рост потока не создаёт
  постоянных расходов, только переменные (см. [MONETIZATION.md](MONETIZATION.md)).
