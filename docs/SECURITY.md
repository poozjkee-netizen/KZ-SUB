## 1. Требует твоих действий — по убыванию срочности

### 🔴 Отозвать токен бота, который попал в переписку

Токен `8600039142:AAE…` был прислан в чат при настройке. Всё, что попало в
переписку, считается скомпрометированным: по токену можно читать все сообщения
бота и писать от его имени.

```
@BotFather → /mybots → NP SUB → API Token → Revoke current token
```

Новый токен ввести **только в терминале**, не пересылая никуда:

```
fly secrets set KZSUB_TELEGRAM_BOT_TOKEN=НОВЫЙ_ТОКЕН
```

### 🔴 Задать секрет вебхука (иначе бот теперь не работает)

Содержимое Telegram-Update целиком задаёт тот, кто его прислал — включая поле
`from.id`. Подделав его под твой Telegram ID, посторонний нажал бы кнопку
«Подтвердить» за тебя и **выдал себе платную лицензию**. Единственное, что это
предотвращает, — секрет вебхука.

Раньше он был необязательным (без него запросы просто не проверялись). Теперь
шлюз **отказывается обслуживать вебхук без секрета** — это осознанное изменение
поведения: лучше неработающий бот, чем открытая выдача ключей.

```
fly secrets set KZSUB_TELEGRAM_WEBHOOK_SECRET=$(openssl rand -hex 32)
```
```
fly deploy --remote-only
```
```
fly ssh console -C "python -m app.telegram_bot set-webhook https://kzsub-gateway.fly.dev/telegram/webhook"
```

Проверить: `fly ssh console -C "python -m app.telegram_bot webhook-info"` —
в ответе должно быть `"has_custom_certificate": false` и отсутствие ошибок
доставки.

### 🟡 Сменить внутренний ключ воркера

`KZSUB_RUNPOD_WORKER_KEY` по умолчанию `gateway-internal` — значение лежит
открытым текстом в репозитории. Само по себе не критично (чтобы им
воспользоваться, нужен ещё и Runpod API-ключ), но дефолт из публичного кода
секретом быть не должен:

```
fly secrets set KZSUB_RUNPOD_WORKER_KEY=$(openssl rand -hex 24)
```

То же значение прописать в переменных окружения эндпоинта Runpod.

### 🟡 Настройки GitHub (5 минут в браузере)

| Что | Где | Зачем |
|---|---|---|
| Двухфакторная аутентификация | Settings → Password and authentication | Аккаунт с доступом к коду и Pages |
| Secret scanning + Push protection | репозиторий → Settings → Code security | Не даст запушить токен/ключ по ошибке |
| Dependabot alerts | там же | Уязвимости в зависимостях (`fastapi`, `uvicorn`) |
| Защита ветки по умолчанию | Settings → Branches → Add rule | Запрет force-push и удаления ветки |
| Actions → Workflow permissions | Settings → Actions → General | Поставить «Read repository contents» |

Права в нашем workflow уже минимальны (`contents: read`, `pages: write`,
`id-token: write`) — но общая настройка репозитория задаёт потолок для всех
будущих workflow.

## 2. Что исправлено кодом

### Загрузка без ключа заполняла диск (главная находка)

`file: UploadFile = File(...)` — это зависимость FastAPI, и она разбирает
multipart **до** первой строки обработчика. Значит проверка ключа внутри
`_transcribe` наступала уже после того, как тело целиком легло во временный
файл. Любой человек без ключа мог отправить сколько угодно гигабайт и забить
диск машины.

Теперь `app/limits.py` + middleware в `main.py` проверяют **до разбора формы**:

- наличие `X-API-Key` → иначе `401`;
- `Content-Length` присутствует → иначе `411`;
- размер ≤ `KZSUB_MAX_UPLOAD_MB` (150 МБ) → иначе `413`.

150 МБ рассчитаны на худший честный случай: 10 минут 48 kHz stereo от панели
до 1.4.0. Свежая панель шлёт 16 kHz mono — около 19 МБ.

### Несколько тяжёлых прогонов разом = OOM

Каждый прогон держит в памяти исходник, конвертированный WAV и base64-куски.
На 1 ГБ памяти три больших ролика одновременно кладут процесс — это уже
случалось на 512 МБ. Теперь `KZSUB_MAX_CONCURRENT_JOBS` (2) ограничивает
одновременность; лишние запросы **ждут** в очереди до
`KZSUB_JOB_WAIT_SECONDS` (120 с), и только потом получают `503` с `Retry-After`.
Ожидание выбрано намеренно: распознавание и так длится десятки секунд, очередь
для пользователя выглядит как «чуть дольше», а мгновенный отказ — как поломка.

Второй запрос с тем же ключом не встаёт в очередь, а сразу получает `409`:
панель шлёт по одному ролику, значит это либо повтор, либо попытка занять
сервер целиком.

### Сравнение секретов по времени

Секрет вебхука сравнивался обычным `!=` — время сравнения зависит от того,
сколько первых символов угадано. Теперь `hmac.compare_digest`.

### Заголовки ответов API

`X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer` на все
ответы шлюза.

### Лендинг

Content-Security-Policy тегом (GitHub Pages не даёт настраивать заголовки):
`default-src 'none'`, из внешних источников разрешены только шрифты Google,
`connect-src 'none'` — странице некуда и нечего отправлять. `frame-src`,
`object-src`, `form-action`, `base-uri` закрыты. Проверено в браузере:
нарушений политики нет, страница работает.

`'unsafe-inline'` для стилей и скриптов оставлен осознанно — страница
намеренно одностраничная и самодостаточная, весь CSS и JS внутри файла. Это
ослабляет защиту от XSS, но на статической странице без пользовательского
ввода и без обращений наружу вектора для XSS нет.

## 3. Что проверено и оказалось в порядке

- **Секретов в репозитории нет.** `.gitignore` закрывает `.env`, `*.p12`,
  `dist/`; в истории коммитов ключи и сертификаты не встречаются.
- **Ключи лицензий не угадываются**: `secrets.token_urlsafe(24)` — 192 бита.
  Перебор через `/license` бессмысленен.
- **Воркер не проверяет лицензии** и не имеет доступа к их БД — источник правды
  только шлюз. Скомпрометированный воркер не выдаёт ключи.
- **Аудио не хранится**: временный файл удаляется в `finally`. Сбор датасета
  выключен по умолчанию и включается только для явно перечисленных ключей.
- **В метриках нет персональных данных**: ключ и устройство хранятся хешем.

## 4. Известные ограничения (осознанные)

- **Привязка к устройству обходится.** `X-Device-Id` считает сама панель, её
  можно подменить. Это защита от бытового обмена ключом, а не от
  злоумышленника; настоящая защита — квота минут, которую подменить нельзя.
- **Ограничитель одновременности — на процесс.** При нескольких машинах Fly
  лимит станет «на машину». Пока машина одна (`min_machines_running = 1`, а
  SQLite и не позволяет больше) — это и есть глобальный лимит.
- **Оплата подтверждается человеком.** У Kaspi нет публичного API; автоматизация
  здесь означала бы доверять словам клиента.
