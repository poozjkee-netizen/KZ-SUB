# RELEASE PROCESS — как выкатывать NP SUB

У проекта **три деплой-единицы**, и они выпускаются независимо. Всегда сначала
определи, что ты менял, и иди по нужной дорожке.

**Гейт для всех:** перед любым релизом — зелёные тесты (`cd backend && pytest`).

---

## A. Релиз панели (изменения в `plugin/`)

Требуется, когда менялось что угодно в `plugin/` (html/css/js/jsx, пресет, иконка,
манифест). Пользователь получит новую `.zxp`.

1. Прогони тесты (панель тестируется вручную в Premiere — см. RUNBOOK).
2. Подними версию в `plugin/CSXS/manifest.xml`:
   `ExtensionBundleVersion` **и** `Extension Version` (обе!) — иначе установщик не
   распознает обновление. Схема semver: `MAJOR.MINOR.PATCH`.
3. Собери и подпиши:
   ```bash
   ZXPSIGNCMD=~/bin/ZXPSignCmd bash scripts/build-zxp.sh   # → dist/NP-SUB-<версия>.zxp
   ```
   Имя файла содержит версию из манифеста (`NP-SUB-1.4.0.zxp`) — сборки не путаются.
   Подписывай **тем же** `dist/kzsub-cert.p12` (иначе для Premiere это «другой» плагин).
4. Проверь установку из `.zxp` через ZXP Installer (см. DISTRIBUTION).
5. Обнови `CHANGELOG.md`: перенеси [Unreleased] → `[X.Y.Z] — дата`.
6. Тег: `git tag plugin-vX.Y.Z && git push --tags`.
7. Раздай `dist/NP-SUB-<версия>.zxp` пользователям.

## B. Релиз шлюза (изменения в `backend/app/`)

Требуется при правках серверной логики (нарезка, стиль, квоты, ключи,
device-binding, прокси). Пользователю ничего переустанавливать не надо.

1. `cd backend && pytest` — зелёные.
2. Деплой:
   ```bash
   cd backend && fly deploy --remote-only
   ```
3. Секреты (при изменении): `fly secrets set KZSUB_...=...` (см. HOSTING).
4. Проверка: `curl https://kzsub-gateway.fly.dev/health` и сквозной прогон с ключом.
5. `CHANGELOG.md`: строка в [Unreleased] c пометкой **[Шлюз]** (версию панели НЕ поднимаем).

## C. Релиз GPU-воркера (изменения в `backend/serverless/`)

Требуется при правках обработчика/образа воркера.

> **Что реально требует пересборки (после ADR-15):** только распознавание —
> `transcribe.py` (`decode_options()`) и дефолты декодирования в `config.py`
> (признак: комментарий «живёт в ВОРКЕРЕ»). Нарезка, оформление и постобработка
> переехали на шлюз и катятся `fly deploy`.
>
> Образ всё ещё копирует весь `backend/app/`, но исполняет из него только
> распознавание. Если сомневаешься — посмотри в лог прогона: предупреждение
> «воркер вернул уже нарезанные сегменты» означает, что на эндпоинте старый
> образ и он делает больше, чем должен.

1. `cd backend && pytest` (общая логика покрыта).
2. Собери и запушь образ с **новым тегом** (не перезаписывай `:v1`):
   ```bash
   cd backend
   docker build --platform linux/amd64 -f serverless/Dockerfile.runpod \
     -t <docker-user>/kzsub-runpod:vN .
   docker push <docker-user>/kzsub-runpod:vN
   ```
3. В Runpod → эндпоинт → сменить образ на `:vN` → сохранить.
4. Прогрев: первый запрос после смены образа — «холодный».
5. `CHANGELOG.md`: строка в [Unreleased] c пометкой **[Воркер]**.

## Версионирование и теги
- **Панель** — semver, тег `plugin-vX.Y.Z`, синхронно с манифестом.
- **Шлюз/воркер** — не версионируются для пользователя; фиксируются в CHANGELOG
  датой и (для воркера) тегом образа `:vN`.
- Патч (`Z`) — фиксы/тексты; минор (`Y`) — новые фичи панели; мажор (`X`) —
  несовместимые изменения (напр. миграция на UXP).

## Роллбэк
- **Панель:** раздать предыдущую `.zxp` (храни артефакты релизов).
- **Шлюз:** `fly deploy` предыдущего коммита или `fly releases` → откат.
- **Воркер:** вернуть у эндпоинта предыдущий тег образа `:v(N-1)`.
