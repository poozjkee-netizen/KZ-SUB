## Цель

Выдержать рост потока без деградации: обработка больших файлов, много
одновременных запросов, мультирегион. Включать по мере реальной нагрузки, не
раньше — сейчас текущая схема (один инстанс + serverless-GPU) справляется.

## Описание

Заглушки перечислены в STATUS §6 и ROADMAP «Этап 4». Архитектура сознательно
простая (см. [DECISIONS.md](../DECISIONS.md)): SQLite на томе, временный файл на
диске, один GPU-эндпоинт. Интерфейсы модулей позволяют заменить хранилища без
переписывания логики.

## Подзадачи

- [ ] **Длинные файлы > 4 минут** (снять текущий потолок). У Runpod лимит 10 MiB
      на тело `/run`, аудио шлётся инлайн base64 → даже в 16 kHz mono влезает
      ~4 минуты (`KZSUB_MAX_AUDIO_SECONDS=240`). Варианты: (а) нарезка аудио на
      части на шлюзе (stdlib `wave`), транскрибация по кускам, склейка сегментов
      со сдвигом тайм-кодов; (б) загрузка аудио в объектное хранилище и передача
      воркеру URL вместо base64. Сейчас файлы длиннее отсекаются с кодом 413.
- [ ] **Очередь задач + пул GPU-воркеров + автоскейл** (горизонтальное масштабирование обработки)
- [ ] **Объектное хранилище + пресайн-URL** для больших аудиофайлов (вместо временного файла на диске; заодно снимает лимит 4 мин выше)
- [ ] **Postgres вместо SQLite** при мультирегионе (интерфейс `licenses` тот же)
- [ ] Нагрузочное тестирование и определение порогов, при которых включать каждый пункт

## Definition of Done

- Есть понятные триггеры (по метрикам из [06-analytics](06-analytics.md)), при которых включается каждый механизм масштабирования.
- При росте нагрузки система деградирует плавно, а не падает; большие файлы обрабатываются надёжно.

## Заметки

- Не масштабируй преждевременно — «Сначала работает, потом красиво» (CLAUDE.md §2).
- Переезд БД: модуль `licenses` спроектирован так, что смена SQLite→Postgres не меняет вызывающий код.
- Надёжность GPU уже решена (ADR-13) — это про пропускную способность и большие файлы.
