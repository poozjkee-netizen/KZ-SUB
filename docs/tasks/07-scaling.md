## Цель

Выдержать рост потока без деградации: обработка больших файлов, много
одновременных запросов, мультирегион. Включать по мере реальной нагрузки, не
раньше — сейчас текущая схема (один инстанс + serverless-GPU) справляется.

## Описание

Заглушки перечислены в STATUS §6 и ROADMAP «Этап 4». Архитектура сознательно
простая (см. [DECISIONS.md](../DECISIONS.md)): SQLite на томе, временный файл на
диске, один GPU-эндпоинт. Интерфейсы модулей позволяют заменить хранилища без
переписывания логики.

## Подзадачи

- [x] **Длинные файлы (нарезка на части)** — реализовано. Шлюз режет 16 kHz mono
      аудио на куски по `KZSUB_CHUNK_SECONDS` (180 c) точкой реза по тишине
      (`app/audio_chunk.py`, stdlib `wave`/`audioop`), гонит каждый через Runpod
      и склеивает сегменты со сдвигом тайм-кодов (`main._runpod_transcribe`).
      Лимит файла поднят обратно до 10 мин (`KZSUB_MAX_AUDIO_SECONDS=600`).
      Дальнейший рост (десятки минут) упрётся в память/время — тогда объектное
      хранилище + URL и/или параллельные куски.
- [ ] **Очередь задач + пул GPU-воркеров + автоскейл** (горизонтальное масштабирование обработки; заодно параллельная обработка кусков)
- [ ] **Объектное хранилище + пресайн-URL** для больших аудиофайлов (вместо временного файла на диске; снимает лимит по памяти при десятках минут)
- [ ] **Postgres вместо SQLite** при мультирегионе (интерфейс `licenses` тот же)
- [ ] Нагрузочное тестирование и определение порогов, при которых включать каждый пункт

## Definition of Done

- Есть понятные триггеры (по метрикам из [06-analytics](06-analytics.md)), при которых включается каждый механизм масштабирования.
- При росте нагрузки система деградирует плавно, а не падает; большие файлы обрабатываются надёжно.

## Заметки

- **Эталон производительности (2026-07-26, прод):** ролик 551 c (9:11) →
  файл 17,6 МБ (16 kHz mono, 32 КБ/с), конвертация 0,0 c (passthrough),
  4 куска по 180 c при `CHUNK_CONCURRENCY=3`, распознавание **98 c**, 523 сегмента.
  Разброс по кускам 2–98 c — холодные старты воркеров Runpod; итоговое время равно
  самому медленному куску, поэтому дальнейшее ускорение — это прогрев/Max Workers
  у эндпоинта, а не код шлюза.
- Не масштабируй преждевременно — «Сначала работает, потом красиво» (CLAUDE.md §2).
- Переезд БД: модуль `licenses` спроектирован так, что смена SQLite→Postgres не меняет вызывающий код.
- Надёжность GPU уже решена (ADR-13) — это про пропускную способность и большие файлы.
