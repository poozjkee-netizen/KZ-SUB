# CLAUDE.md — постоянная инструкция для разработки NP SUB

> Этот файл читают все будущие сессии Claude Code и любой новый разработчик.
> Он описывает, **как устроен проект и как в нём работать, не ломая неочевидное.**
> Держи его актуальным: меняешь правило/архитектуру — обнови и этот файл.

---

## 1. Что это за проект

**NP SUB** — плагин для Adobe Premiere Pro, который автоматически распознаёт
**казахскую речь** и вставляет субтитры на таймлайн. Premiere «из коробки» не
транскрибирует казахский — это и есть решаемая боль.

- **Продуктовое имя:** NP SUB.
- **Внутренний идентификатор:** `kzsub` (в env-префиксе `KZSUB_`, именах
  Fly-приложения `kzsub-gateway`, Docker-образа `kzsub-runpod`, bundle id
  `kz.kzsub.panel`). **Внутренние `kzsub`-идентификаторы НЕ переименовываем** —
  они невидимы пользователю, а переименование ломает деплой. «NP SUB» — только
  для того, что видит пользователь (имя расширения, заголовки доков).

**Ядро ценности — не код панели, а качество распознавания казахского.**
Панель копируется за неделю; хорошая ASR-модель — нет.

## 2. Философия

- **Сначала работает, потом красиво.** Продукт живой и уже приносит субтитры.
- **Ценность на сервере, тонкий клиент.** Тяжёлое (ASR) — только на бэкенде.
  Панель максимально простая: одна кнопка, техника спрятана.
- **Дешёвый старт.** Serverless-GPU с оплатой за секунды; шлюз на копеечном CPU.
- **Меньше зависимостей — меньше боли.** Core-логика бэкенда пишется без тяжёлых
  пакетов, чтобы оставаться тестируемой где угодно.
- **Честность к пользователю.** Ошибки — понятным языком (каз/рус), без техжаргона.

## 3. Архитектура (обязательно понимать перед правками)

Три независимые деплой-единицы:

```
┌────────────────────┐   HTTPS    ┌────────────────────┐   Runpod API  ┌──────────────────┐
│  Панель (CEP)      │ ─────────▶ │  Шлюз (FastAPI)    │ ────────────▶ │ GPU-воркер       │
│  plugin/  → .zxp   │ multipart  │  backend/ → Fly.io │  /run+/status │ serverless/→Runpod│
│  у пользователя    │ ◀───────── │  ключи+квоты+      │ ◀──────────── │  Whisper large-v3│
│                    │   .srt     │  device-binding    │   сегменты    │                  │
└────────────────────┘            └────────────────────┘               └──────────────────┘
```

### Ключевая деталь: бэкенд имеет ДВА режима (`backend/app/main.py`)
- **Локальный** — если `KZSUB_RUNPOD_ENDPOINT_ID`/`KZSUB_RUNPOD_API_KEY` НЕ заданы:
  Whisper крутится прямо в процессе (`transcribe.py`). Для разработки на своей машине.
- **Прокси (прод)** — если заданы: аудио уходит в Runpod (`runpod_client.py`),
  шлюз только оркестрирует. Так работает Fly-шлюз.

Один и тот же `main.py` обслуживает оба режима — не разноси их по разным приложениям.

### Конвейер субтитров (общий для обоих режимов)
`transcribe` (сегменты+пословные тайм-коды) → `segmentation` (нарезка: `word`
караоке / `phrase`) → `style` (регистр/пунктуация) → `srt`. В прокси-режиме
нарезку/стиль делает воркер (`serverless/runpod_handler.py`), шлюз получает
готовые сегменты.

### 🔑 ЗОЛОТОЕ ПРАВИЛО: что и как деплоится
| Что изменил | Как выкатить | Пользователю переустанавливать? |
|---|---|---|
| **Панель** (`plugin/`: html/css/js/jsx/пресет/иконка) | поднять версию в манифесте → `scripts/build-zxp.sh` → раздать `.zxp` | **Да** |
| **Логика сервера** (`backend/app/`) | `fly deploy --remote-only` | Нет |
| **GPU-воркер** (`backend/serverless/`) | пересобрать образ → push → сменить образ у Runpod-эндпоинта | Нет |

Подробности релизов — [`docs/RELEASE_PROCESS.md`](docs/RELEASE_PROCESS.md).

## 4. Правила изменения кода

- **Не переписывай архитектуру ради красоты.** Она осознанная (см.
  [`docs/DECISIONS.md`](docs/DECISIONS.md)). Любое изменение — с явной причиной.
- **Меняй минимально необходимое.** Точечные правки предпочтительнее «больших уборок».
- **Уважай два режима бэкенда** — правка не должна ломать ни локальный, ни прокси.
- **Core-логика без тяжёлых зависимостей.** Модули `srt.py`, `quota.py`,
  `segmentation.py`, `style.py`, `devices.py`, `config.py` **не должны** импортировать
  `fastapi`/`faster_whisper` на уровне модуля (Whisper — лениво внутри функций).
  Это держит их dep-free-тестируемыми.
- **Конфиг — только через `config.py`** и префикс `KZSUB_`. Новую настройку
  добавляй туда + в `backend/.env.example` + в таблицу `backend/README.md`.
- **Панель: не ломай контракт с бэкендом.** Заголовки `X-API-Key`, `X-Device-Id`,
  multipart `file`. ID DOM-элементов, на которые завязан `main.js`, менять нельзя
  без синхронной правки JS.

## 5. Правила рефакторинга

- Рефактори, только когда это: (а) упрощает конкретную будущую задачу, или
  (б) убирает реальное дублирование/баг. Не «на всякий случай».
- Один рефакторинг = один коммит, отдельно от функциональных изменений.
- Перед рефактором прогони тесты; после — тоже. Поведение не меняется.
- Не трогай `.claude/skills/ui-ux-pro-max/` и `design-system/` — это вендоренные
  артефакты, живут своей жизнью.

## 6. Правила написания новых функций

1. Реши, **куда** относится фича: панель / шлюз-логика / воркер. От этого зависит
   деплой (см. золотое правило).
2. **Серверную фичу предпочитай клиентской** — она катится без пересборки `.zxp`
   у пользователей. Если можно сделать на бэкенде — делай там.
3. Настройки — через `config.py` (с дефолтом, чтобы не ломать прод по умолчанию).
4. Добавь/обнови тест (см. §11).
5. Обнови документацию и `CHANGELOG.md` (см. §8, §10).

## 7. Требования к качеству кода

- **Python:** стиль как в существующих модулях — короткие функции, типы в
  сигнатурах, docstring с назначением, комментарии объясняют «почему», а не «что».
- **JS (панель):** ES5-совместимость (движок CEF в CEP старый), без сборщиков и
  фреймворков. Никаких внешних CDN — всё локально (офлайн-устойчивость).
- **ExtendScript (`host.jsx`):** каждая функция возвращает строку-результат или
  `"ERROR: ..."`; всё оборачивай в try/catch. Помни про кроссплатформенность (Win/Mac).
- Ошибки пользователю — двуязычные (каз/рус) через хелпер `bi()`/`biErr()` в `main.js`.

## 8. Правила оформления коммитов

- **Язык:** русский, повелительно/итогом: «Добавь X», «Почини Y», «Прокси-режим…».
- **Первая строка** — суть до ~72 символов. Далее пустая строка и, при необходимости,
  тело: что и **зачем**.
- **Один коммит — одна логическая единица.** Не мешай рефактор с фичей.
- **Не упоминай** внутренний идентификатор модели/служебные детали среды в
  сообщениях коммитов.
- В конце сообщения — трейлеры Co-Authored-By / Claude-Session (как настроено в среде).
- **Коммить и пушь только по явной просьбе** пользователя (в этом проекте — ветка
  `claude/premiere-kazakh-subtitles-plugin-xld1pz`).

## 9. Соглашения по именованию

- **Env-переменные:** `KZSUB_<ИМЯ>` (см. `config.py`). Не заводи конфиг мимо этого.
- **Python:** модули и функции `snake_case`, классы `CamelCase`. Модуль = одна зона
  ответственности (`quota`, `devices`, `segmentation`, `style`, `srt`, `transcribe`,
  `runpod_client`).
- **Инфра-идентификаторы фиксированы:** `kzsub-gateway` (Fly), `kzsub-runpod`
  (Docker), `kz.kzsub.panel` (bundle id), `kzsub_data` (том), `gateway-internal`
  (внутренний ключ воркера). Менять — только осознанно и синхронно везде.
- **Продуктовые тексты** (UI, заголовки доков, имя расширения, файл `NP-SUB.zxp`) —
  «NP SUB».

## 10. Правила обновления документации

- Меняешь поведение/настройку/процесс — **обнови соответствующий док в том же
  коммите.** Расхождение кода и доков хуже отсутствия доков.
- Новая env-переменная → `config.py` + `backend/.env.example` + таблица в
  `backend/README.md`.
- Значимое архитектурное решение → короткая запись в `docs/DECISIONS.md`.
- Любое изменение, влияющее на пользователя/релиз → строка в `CHANGELOG.md`.
- Held source of truth: реестр доков — §12 и [`docs/README.md`](docs/README.md).

## 11. Требования к тестированию

- **Два класса тестов** в `backend/tests/`:
  - **dep-free** (`test_srt`, `test_quota`, `test_segmentation`, `test_style`,
    `test_devices`) — запускаются без тяжёлых пакетов: `python tests/test_x.py`.
    Любая новая core-логика обязана иметь такой тест.
  - **интеграционные** (`test_api`) — HTTP-контракт `/transcribe` с замоканной
    моделью; нужен `fastapi`/`httpx`: `pytest tests/test_api.py`.
- **Гейт перед деплоем/сборкой `.zxp`:** прогнать тесты (локально `pytest`, в CI —
  автоматически). Красные тесты = не деплоим.
- Тест пишем в том же коммите, что и фичу/фикс. Тест должен падать до фикса и
  зеленеть после.
- Панель/ExtendScript автотестами не покрываются — проверяются вручную в Premiere
  (см. [`docs/RUNBOOK.md`](docs/RUNBOOK.md)); поэтому логику по возможности держим на бэкенде.

## 13. Быстрые команды

```bash
# Тесты (dep-free — без установки тяжёлых пакетов)
cd backend && python tests/test_srt.py && python tests/test_quota.py \
  && python tests/test_segmentation.py && python tests/test_style.py \
  && python tests/test_devices.py

# Тесты (все, с зависимостями)
cd backend && pytest

# Локальный бэкенд
bash scripts/run-backend.sh

# Деплой шлюза
cd backend && fly deploy --remote-only

# Сборка подписанного плагина
ZXPSIGNCMD=~/bin/ZXPSignCmd bash scripts/build-zxp.sh   # → dist/NP-SUB.zxp
```
